While local thread locks prevent race conditions within a single process, distributed locks are required to enforce mutual exclusion across an entire network of independent machines. This chapter explores how to safely coordinate exclusive access to shared resources, handle node crashes using leases, and navigate the subtle race conditions that make distributed locking so dangerous.

### Topics Covered

* **[5.3.1. Lock Fundamentals: Mutual Exclusion in Distributed Systems](/distributed-systems/en/coordination/distributed-locking/lock-fundamentals/)**: Defines the core requirements for distributed locks, balancing strict safety (mutual exclusion) with liveness (deadlock avoidance).
* **[5.3.2. Lease-Based Locking: TTL, Renewal, and Expiry Semantics](/distributed-systems/en/coordination/distributed-locking/lease-based-locking/)**: Explains why infinite locks cause permanent deadlocks and how to implement time-bound leases with background heartbeat renewals.
* **[5.3.3. Fencing Tokens: Preventing Stale Lock Holders](/distributed-systems/en/coordination/distributed-locking/fencing-tokens/)**: Addresses the critical flaw where a paused process wakes up believing it still holds a lock, using monotonically increasing tokens to reject stale writes at the storage layer.
* **[5.3.4. Redlock Algorithm: The Redis Distributed Lock Debate](/distributed-systems/en/coordination/distributed-locking/redlock/)**: Analyzes the popular Redis-based locking algorithm, its reliance on physical wall-clock time, and the famous architectural debate surrounding its safety guarantees.
* **[5.3.5. ZooKeeper and etcd Recipes: Production Lock Implementations](/distributed-systems/en/coordination/distributed-locking/zookeeper-etcd-recipes/)**: Examines how true consensus stores use ephemeral nodes and strict event ordering to provide bulletproof, production-ready lock managers.
